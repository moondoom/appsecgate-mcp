# ADR-001: Fingerprint и семантическая дедупликация находок

**Статус:** Proposed
**Дата:** 2026-10-14
**Контекст:** T1, T10, T13, §9.1 architecture.md
**Решает:** стабильность fingerprint + кросс-сканерный дедуп + различение близких находок

---

## 1. Контекст

Дедупликация находок — фундамент трёх подсистем AppSecGate:

* `shown_findings.db` (PK = fingerprint) — журнал показанного для `block_on_unresolved_local`;
* `suppressions` (PK = fingerprint) — фильтр подавлений;
* `verify_fix` — сопоставление «до/после» по fingerprint.

Текущая реализация ломается в двух местах.

### 1.1. Недетерминированный fingerprint (T10)

`fingerprint = sha256(rule_id + file_path + normalize_snippet(snippet))[:16]`.

`rule_id` входит в ключ, а `Deduplicator._collapse()` выбирает «выжившего» по порядку raw-находок Gitleaks. Порядок между прогонами нестабилен → один и тот же секрет получает то `github-pat`, то `generic-api-key`, fingerprint меняется. Последствия: `suppression` не срабатывает, `verify_fix` не находит находку, `export_snapshot` шумит, `query_findings_db` даёт разное число строк для `scan_file` и `scan_project` (B2).

### 1.2. Разные сканеры — разные fingerprint одной проблемы (T1)

Даже с детерминированным tie-break остаются случаи, когда **разные сканеры** находят **одну проблему** с разными `rule_id` (Semgrep `hardcoded-credentials` + Gitleaks `generic-api-key` на одной строке). Существующий `deduplicate_families()` покрывает это эвристикой `(file_path, line_start // 20, normalized_body)` — работает, но грубо: **схлопывает все находки в 20-строчном окне**, что для файлов с частыми паттернами (10 `eval()` подряд) даёт ложные схлопывания.

### 1.3. Требования

1. Fingerprint детерминирован: один и тот же код → один и тот же fp на любой машине и в любом прогоне.
2. Разные сканеры, описывающие одну проблему, должны предлагаться к мерджу (но не мерджиться молча).
3. Похожие, но **разные** находки в одном файле (10 `eval` в разных местах) не должны схлопываться.
4. Сдвиг строки при рефакторинге (+1..+3 строки) не должен ломать идентичность находки.
5. Офлайн-первый: без сетевых вызовов, модель в образе, RAM < 1 ГБ.

---

## 2. Решение

**Двухуровневый пайплайн.**

**Уровень 1 — детерминированный fingerprint (hash).** Дешёвый, всегда включён, PK всех хранилищ. Даёт стабильность, но не различает «одна проблема — разные сканеры».

**Уровень 2 — семантическая близость (эмбеддинги + decay по строке).** Опциональный, работает **поверх** fingerprint-дедупа. Выдаёт либо авто-мердж, либо `suspected_duplicate_of` в ответе агенту. Никогда не заменяет fp, только дополняет.

### 2.1. Ключевой принцип разделения

* В **вектор** идёт всё **семантически стабильное**: `rule_id`, `category`, `normalized_code`.
* **Строка не входит в вектор.** Она участвует в итоговом score через множитель `exp(-Δline / σ)`. Причина: языковые модели не интерполируют числа — `line:42` и `line:43` для них так же далеки, как `line:42` и `line:1000`.
* **Категория определяет σ.** Секреты привязаны к строке жёстко, SAST — мягко, SCA — не привязаны вовсе.

## 3. Fingerprint: детерминированная схема

### 3.1. Формула

```
fingerprint = sha256(rule_id + "\x00" + file_path + "\x00" + normalized_snippet)[:16]
```

Формула **не меняется** относительно текущей. Меняется только **что попадает в дедуп до её вычисления**.

### 3.2. Детерминированный tie-break в `_collapse()`

Перед выбором «выжившего» raw-находки сортируются по стабильному ключу:

```python
SCANNER_PRIORITY = {
    "gitleaks":   0,   # секреты — приоритетнее, у него точнее rule_id
    "trufflehog": 1,
    "semgrep":    2,
    "trivy":      3,
}

RULE_PRIORITY = {
    # Внутри Gitleaks: конкретные паттерны > generic
    "github-pat":      0,
    "aws-access-key":  0,
    "private-key":     0,
    "generic-api-key": 10,
    # внутри Semgrep: конкретные правила > broad
}

def sort_key(finding):
    return (
        SEVERITY_RANK[finding.severity],           # CRITICAL=0, HIGH=1, ...
        SCANNER_PRIORITY.get(finding.scanner, 99),
        RULE_PRIORITY.get(finding.rule_id, 50),
        finding.rule_id,                            # лексикографически — финальный tie-break
    )

raw_findings.sort(key=sort_key)
winner = raw_findings[0]                            # → fingerprint считается по нему
```

**Инвариант:** для одного и того же множества raw-находок (независимо от порядка поступления) `winner` всегда один. Это и есть фикс T10.

### 3.3. Что нормализуется в snippet

```python
def normalize_snippet(snippet: str) -> str:
    s = strip_comments(snippet)          # # ... , // ... , /* ... */
    s = collapse_whitespace(s)           # любые пробелы/табы/переносы → один пробел
    s = s.strip()
    return s
```

**Не** абстрагируем идентификаторы и литералы: `eval(x)` и `eval(user_input)` — разные проблемы.

### 3.4. Что НЕ входит в fingerprint

* Номер строки — сдвиг рефакторинга не должен менять fp.
* `line_end` — по той же причине.
* `severity` — может поменяться при обновлении правил; fp не должен «плыть».
* `message` — локализация/формулировка правил меняется между версиями.
* `snippet` — **входит**, но нормализованный.

### 3.5. Границы применимости

Fingerprint **не различает**:
* разные сканеры на одной проблеме (это работа уровня 2);
* две находки одного правила с идентичным нормализованным сниппетом в одном файле (приемлемо — редкий кейс, T1 это уже принимает).

## 4. Семантический уровень: эмбеддинги + line decay

### 4.1. Что попадает в вектор

```
text_for_embedding = f"{rule_id} | {category} | {normalized_code}"
```

* `rule_id` — якорь семантики правила.
* `category` (`sast|secret|sca|iac|license`) — грубый класс.
* `normalized_code` — тот же, что для fingerprint (стабильно к комментариям/пробелам).

**Строка не входит в текст.**

### 4.2. Модель

* `all-MiniLM-L6-v2` в ONNX-формате (fp16), ~90 МБ.
* Runtime: `onnxruntime` (без `torch`, без `sentence-transformers`).
* Размерность: 384, float32 в БД.
* `model_id` + `model_hash` хранятся рядом с эмбеддингом — при смене модели вектора пересчитываются.

### 4.3. Combined score

```python
def combined_score(a, b, sigma_by_category):
    cos = cosine_sim(a.embedding, b.embedding)                # 0..1
    delta = abs(a.line_start - b.line_start)
    sigma = sigma_by_category[a.category]
    decay = math.exp(-delta / sigma)
    return cos * decay
```

Свойства `exp`-decay:

| Δline / σ | decay | Эффект |
|---|---|---|
| 0 | 1.00 | позиция идентична |
| 0.5 | 0.61 | небольшой сдвиг |
| 1 | 0.37 | заметный сдвиг |
| 2 | 0.14 | далеко |
| ≥ 5 | < 0.01 | практически «разные» |

Для σ=30 (SAST): сдвиг на 15 строк → decay 0.61; сдвиг на 60 строк → 0.14; сдвиг на 150 → 0.007.

### 4.4. σ по категориям (конфигурируемо)

| Категория | σ (строк) | Обоснование |
|---|---|---|
| `secret` | 3 | Секрет привязан к переменной/строке, сдвиг на 5 строк — уже другая переменная |
| `sast` | 30 | Функция растёт, код переезжает на 10–30 строк при рефакторинге |
| `iac` | 10 | YAML/TF блочный, сдвиг невелик |
| `sca` | 10⁶ | CVE привязаны к пакету, строка нерелевантна — decay ≈ 1 |

```yaml
# config/default.yaml
dedup:
  semantic:
    enabled: false                     # opt-in до стабилизации порогов
    top_k: 10
    sigma_by_category:
      secret: 3
      sast: 30
      iac: 10
      sca: 1000000
    thresholds:
      auto_merge: 0.95
      suspect: 0.80
```

### 4.5. Пороги и действия

| combined_score | Действие |
|---|---|
| ≥ 0.95 | **Авто-мердж:** новый finding не создаётся, у существующего `show_count++`, `last_shown_at=now` |
| 0.80 – 0.95 | **Подозрение:** находка сохраняется с отдельным fingerprint, в ответе `suspected_duplicate_of: [{fingerprint, score}]` |
| < 0.80 | Новая независимая находка |

Пороги — стартовая гипотеза. Калибруются на E2E-полигоне (см. §8).

### 4.6. Почему не «line в вектор»

Рассмотренные альтернативы (§9.1) — Fourier-фичи позиции, хеширование line-номера, positional encoding — все требуют изменений в тексте эмбеддинга. Это либо делает модель нестабильной к сдвигу, либо непрозрачно для дебага. Гибрид «вектор + скаляр» прозрачен: `cosine` объясняет семантику, `decay` объясняет позицию, оба параметра тюнятся независимо.

## 5. Хранилище

### 5.1. Новая таблица `finding_embeddings`

Отдельная БД или таблица в `scan_cache.db` (не трогаем `shown_findings.db`):

```sql
CREATE TABLE finding_embeddings (
    fingerprint       TEXT PRIMARY KEY,       -- FK логически, но не SQL-FK:
                                              -- suppressed/GC'd находки могут вернуться
    embedding         BLOB NOT NULL,          -- float32[384] = 1536 байт
    line_start        INTEGER NOT NULL,       -- для decay
    category          TEXT NOT NULL,          -- для выбора σ
    model_id          TEXT NOT NULL,          -- "all-MiniLM-L6-v2"
    model_hash        TEXT NOT NULL,          -- sha256 весов ONNX
    first_embedded_at TIMESTAMP NOT NULL,
    last_seen_at      TIMESTAMP NOT NULL,     -- для GC
    scan_count        INTEGER DEFAULT 1
);

CREATE INDEX idx_emb_last_seen ON finding_embeddings(last_seen_at);
CREATE INDEX idx_emb_category  ON finding_embeddings(category);
```

### 5.2. Почему эмбеддинг считается по fingerprint

Ключевое решение архитектуры: **эмбеддинг персистентен по fingerprint**, а не по raw-находке.

* Старый fingerprint → запись уже есть → эмбеддинг **не пересчитывается** (0 мс).
* Новый fingerprint → считается **один раз за всё время жизни** находки (5–20 мс).
* Тот же fingerprint в следующих сканах → **нулевая стоимость** на уровне 2.

Стоимость за скан: только для **новых** fingerprint после уровня 1. На типичном diff это 3–10 записей → **~50–200 мс** прироста.

### 5.3. Поиск ближайших соседей

* Размер индекса: 10 000 fingerprint × 384 × 4B ≈ **15 МБ**. Brute-force cosine на numpy — **~10 мс** для 10K.
* FAISS/Annoy **не нужен** до ~100K записей. YAGNI до Фазы 2.
* Top-K = 10, затем ре-ранжирование по `combined_score` — дешёво.

## 6. Пайплайн

```
raw findings (N ~ 50–200)
   │
   ├─[1] Детерминированная сортировка (§3.2) + _collapse
   │
   ├─[2] deduplicate_families() (существующий эвристический)
   │
   Уникальные по fingerprint (M ~ 10–30)
   │
   ├─[3] semantic_dedup.enabled?
   │      нет → возврат как есть
   │      да  ↓
   │
   ├─[4] для каждого fp:
   │      есть в finding_embeddings? → берём BLOB, last_seen_at=now
   │      нет → embed(text_for_embedding) → INSERT
   │
   ├─[5] top-K по cosine среди проиндексированных
   │
   ├─[6] combined_score = cos × exp(-Δline / σ[category])
   │
   ├─[7] ≥ auto_merge → мердж (fp существующего сохраняется, show_count++)
   │      0.80..0.95 → пометить suspected_duplicate_of
   │      < 0.80 → независимая находка
   │
   ▼
ScanResult.findings + ScanResult.suspected_duplicates
```

**Бюджет времени на уровне 2 (enabled):**

| Этап | Время |
|---|---|
| Проверка fp в индексе | < 1 мс |
| Эмбеддинг новых (3–10 шт) | 20–150 мс |
| Поиск top-K (10K записей, numpy) | ~10 мс |
| Ре-ранжирование | ~1 мс |
| **Итого** | **~30–160 мс** |

SLA `< 5 сек` на diff не страдает.

## 7. Garbage collection

Критерий удаления из `finding_embeddings`:

```sql
DELETE FROM finding_embeddings
WHERE last_seen_at < :now - :ttl_days
  AND fingerprint NOT IN (
      SELECT fingerprint FROM suppressions
      UNION
      SELECT fingerprint FROM shown_findings WHERE status = 'FIXED'
  );
```

Правила:

* `ttl_days` по умолчанию **180** (полгода). Конфигурируемо.
* Suppressed и verified-fixed **не удаляются** — иначе при регрессии находки история испарится.
* Запуск GC — при старте контейнера (дешёво: один `DELETE` по индексу) + раз в сутки, если контейнер долгоживущий.
* **Не удаляем по одному `last_seen_at`** без проверки статуса: долгоживущая находка в legacy-файле, которую сканируют раз в месяц, иначе потеряет эмбеддинг.

## 8. Тестирование

### 8.1. Unit

* `test_fingerprint_deterministic`: 100 прогонов `_collapse` на перемешанных raw → один и тот же fingerprint. Регресс на T10.
* `test_line_decay`: `combined_score` убывает с ростом Δline; на σ=30 при Δ=60 score ≈ cos × 0.135.
* `test_embedding_persist`: тот же fp в двух сканах → эмбеддинг считается один раз (mock на embed-функцию, счётчик вызовов = 1).
* `test_similar_evals_not_merged`: 10 фейковых `eval()` в разных строках → после уровня 2 остаются 10 независимыми находками.

### 8.2. E2E на полигоне (vuln-project + other-project)

1. **Кросс-сканерный кейс (T1):** Semgrep + Gitleaks на одном секрете → 1 авто-мердж или `suspected_duplicate_of`.
2. **Рефакторинг:** сдвиг находки на +3 строки → тот же fingerprint (уровень 1), combined_score ≥ 0.95 (уровень 2).
3. **10 eval в одном файле:** 10 независимых находок; между далёкими парами `suspected_duplicate_of` **нет**.
4. **Стабильность между прогонами:** 10 прогонов `scan_project` → идентичный набор fingerprint и `suspected_duplicates`.

### 8.3. NF-замеры

* Пиковая RAM: цель < 700 МБ (было 482, +модель ~90 + индекс ~15 + onnxruntime ~50–100).
* scan_project 8.2–8.7 c → цель не хуже **9.0 c** при включённом семантическом уровне.
* Первый запуск (пустой индекс) vs второй (тёплый) — прирост на тёплом < 20 мс.

## 9. Отвергнутые альтернативы

### 9.1. Line внутри эмбеддинга

* Хеширование `line` в текст: числа не интерполируются моделью, сдвиг +1 даёт cos ≈ 0.
* Fourier-фичи позиции, приклеенные к вектору: работает, но непрозрачно, требует знания длины файла, и параметры (частоты, вес) сложно тюнить. Для одного-двух сценариев — overkill.
* Positional encoding как в трансформерах: требует обучения собственной модели, вне scope.

**Выбрано:** скалярный decay вне вектора — проще, объяснимо, тюнится независимо.

### 9.2. Замена fingerprint на GUID + вектор

Идея: каждая находка получает GUID, дубли отсеиваются по вектору. Отвергнуто:

* Ломает `suppression` (PK по стабильному ID).
* Ломает `block_on_unresolved_local` (журнал показанного требует стабильного ключа).
* Делает `verify_fix` недетерминированным.
* Проблема «нестабильного rule_id» (T10) **не решается** GUID'ом — она решается детерминированным tie-break (§3.2). GUID маскирует симптом, не лечит причину.

### 9.3. Полноценный FAISS + обученная модель для кода

* Overkill для 10K записей. Brute-force numpy — 10 мс.
* CodeBERT/GraphCodeBERT в 4–10× больше MiniLM, требует torch (~700 МБ) → не влезает в бюджет.
* Пересмотр при выходе за 100K записей (Фаза 2+).

### 9.4. Только существующий `deduplicate_families()` без векторов

Оставить как есть. Отвергнуто:

* Окно `line // 20` даёт ложные схлопывания при частых паттернах.
* Не различает «разные правила, одна проблема» и «одно правило, близкие места».
* Векторный уровень добавляет ~150 МБ RAM и ~150 мс на скан — приемлемая цена при бюджете 1 ГБ.

## 10. Последствия

### Положительные

* T10 закрывается детерминированным tie-break **независимо** от семантического уровня.
* T1 закрывается полностью: кросс-сканерные дубли идут через `suspected_duplicate_of` с оценкой уверенности.
* `verify_fix` и `suppression` получают стабильный ключ — T10 и B2.
* Фича-флаг `dedup.semantic.enabled` — можно выкатить инкрементально, не ломая существующие тесты.
* Строка участвует в решении, но не «плывёт» вместе с рефакторингом.

### Отрицательные / риски

* **+150–250 МБ RAM** на модель и индекс. Бюджет 1 ГБ — с запасом, но нужно перемерить на крупном полигоне (T14, п.4).
* **+1 зависимость** (`onnxruntime`) и +90 МБ к образу.
* **Пороги 0.95/0.80** — стартовая гипотеза, требуют калибровки. Если ошибиться в сторону низкого `auto_merge`, получим ложные схлопывания. Поэтому `auto_merge` можно временно поднять до 0.98, а основной путь — `suspected_duplicate_of`.
* **`model_hash`** нужно менять при обновлении весов — иначе старые и новые вектора несравнимы. Автоматическая фоновая реиндексация при несовпадении.
* **σ для новых категорий** — дефолт `sast=30`, требует ручного тюнинга при добавлении экзотических типов.

### Нейтральные

* `deduplicate_families()` **остаётся** — как дешёвый фильтр перед уровнем 2. Уровень 2 его не заменяет, а дополняет.
* Схема `shown_findings.db` не меняется — инвариант для миграций Фазы 2.

| Этап | Содержание | Оценка |
|---|---|---|
| **P0** | Детерминированный tie-break в `_collapse()` (§3.2). Регресс-тест на T10. | 1–2 дня |
| **P0** | GC-политика для `scan_cache.db` (если она уже растёт без ограничений). | 0.5 дня |
| **P1** | `normalization/embeddings.py`: `embed_finding()`, `find_similar()`, `combined_score()`. Спайк на 100 реальных находках для калибровки порогов. | 2–3 дня |
| **P1** | Схема `finding_embeddings`, миграция БД. | 1 день |
| **P1** | Интеграция в `coordinator.scan()` за фича-флагом. Поле `suspected_duplicates` в `ScanResult`. | 2 дня |
| **P2** | E2E-полигон, калибровка σ и порогов, обновление `config/default.yaml`. | 2 дня |
| **P2** | Обновление `architecture.md` §3.4 и §9.1 ссылкой на этот ADR. | 0.5 дня |

**Условие выхода:** E2E-полигон даёт 10/10 одинаковых fingerprint между прогонами, `suspected_duplicate_of` корректно отделяет 10 `eval` в одном файле, пиковая RAM < 800 МБ.

## 12. Открытые вопросы

1. **Текст для эмбеддинга.** Начинаем с `rule_id + category + normalized_code`. Возможно, `message` даст лучшую семантику на кросс-сканерных кейсах — проверить на спайке.
2. **Пороги.** 0.95/0.80 — гипотеза. Калибровка на реальных данных E2E покажет, нужно ли снижать `auto_merge` или повышать `suspect`.
3. **Шаренные эмбеддинги между проектами (T7).** После решения T9 (project_id) можно рассмотреть «предложить подавить в проекте B, если в A уже подавлено». Требует дизайна — вне scope этого ADR.
4. **T13 (SCA, 19 CVE → 1).** Векторный подход **не решает** — нужна отдельная логика агрегации по пакету в `trivy.py`/нормалайзере. Внести отдельной задачей.
5. **Мультиязычность.** `all-MiniLM-L6-v2` — англоцентрична. Для rule_id с русским/иным текстом — проверить качество; при необходимости — `paraphrase-multilingual-MiniLM-L12-v2` (+30 МБ).
