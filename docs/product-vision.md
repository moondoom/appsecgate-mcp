# AppSecGate: Платформа безопасной разработки для AI-эры

> **Версия документа:** 0.2 (draft)
> **Статус:** Product Vision & Roadmap
> **Дата:** 2026-10-08

---

## 1. Видение продукта

**AppSecGate** — это платформа, которая встраивает безопасность в процесс AI-разработки на всех этапах: от написания кода агентом до релиза. Вместо «ещё одного сканера» мы создаём **оркестратор безопасности**, который:

- Работает **локально** (MCP-сервер для AI-агентов и разработчиков).
- Синхронизируется с **центральным сервером** (единый источник правды для команды).
- Интегрируется с **ASOC/ASPM** (DefectDojo, R-Vision, PT ASM и др.).
- Строит **BI-аналитику** по эффективности безопасности.
- Автоматизирует **комплаенс** (ГОСТ Р 56939-2024, ФСТЭК).

### 1.1. Две оси продукта

AppSecGate построен на двух ключевых принципах, которые определяют всю архитектуру и продуктовую логику.

**Ось 1: Свобода локально, ответственность в CI.**

AppSecGate даёт разработчику свободу игнорировать безопасность локально — и эскалирует эту игнорируемую проблему в CI. Разработчик не блокируется в процессе кодинга, но не может «забыть» о том, что видел. Локально — предупреждение, не блок. В CI — та же находка становится gate. Если она была показана локально и не исправлена — теперь она блокирует MR. Не «новая проблема», а «ты знал и решил не чинить».

**Ось 2: Каскадная эскалация.**

AppSecGate решает проблему поэтапно: AI-агент пытается исправить → разработчик пытается исправить → CI блокирует остаток → AppSec разбирает эскалированное → лид принимает риск. Каждый уровень получает только то, с чем не справился предыдущий. AppSec видит не 1000 находок, а только те ~15%, с которыми разработчик не справился. CISO видит не 15%, а 2–3 риска, требующих бизнес-решения.

### 1.2. Ключевой тезис

Безопасность не должна быть «тормозом». Она должна быть **незаметной для разработчика** и **прозрачной для безопасности**. AppSecGate достигает этого за счёт двойного контура gates и каскадной эскалации — двух механизмов, которые вместе образуют единый каркас продукта.

## 2. Проблема, которую решаем

### 2.1. Боль индустрии

- **AI-агенты генерируют код быстрее, чем безопасность успевает его проверять.** 40–50% кода, написанного AI, содержит уязвимости (Veracode, 2026).
- **Сканеры дают шум, а не сигнал.** AppSec-инженеры тратят 60% времени на триаж false positive, а «чёрные лебеди» (Log4Shell, xz backdoor) всё равно проходят.
- **Локальный и CI-скан не синхронизированы.** Разработчик исправил проблему локально, но ASOC об этом не знает. Метрики MTTR врут.
- **Эскалация бинарна.** Сканер нашёл → упало в ASOC → все видят → никто не разбирает. Нет воронки, фильтрующей шум по уровням компетенции.
- **Комплаенс — это бумажная работа.** ГОСТ Р 56939-2024 требует доказательств, которые собираются вручную.

### 2.2. Кого это касается

| Роль | Боль |
|------|------|
| **Developer** | Безопасность мешает, отвлекает, непонятна |
| **Tech Lead** | Не видит, что происходит в команде, не может апрувить дифы |
| **AppSec** | Тонет в шуме, не успевает за разработкой |
| **CISO** | Не может доказать эффективность, не видит реальных рисков |
| **Компания** | Тратит деньги на инструменты, которые не снижают риск |

## 4. Ключевые концепции

### 4.1. Три контура безопасности

```
┌─────────────────────────────────────────────────────────────┐
│  КОНТУР 1: ЛОКАЛЬНЫЙ (MCP + Edge)                            │
│  - Работает на машине разработчика                           │
│  - Сканирует изменённые файлы                                │
│  - Даёт мгновенную обратную связь (секунды)                  │
│  - Warn-only: не блокирует разработчика                      │
│  - Логирует показанные находки для будущего CI-контура       │
│  - Может работать офлайн                                     │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  КОНТУР 2: ЦЕНТРАЛЬНЫЙ (Master Server + CI)                  │
│  - Единый источник правды                                    │
│  - Синхронизация между разработчиками и CI                   │
│  - Двойные gates: локальные (warn) и CI (block)              │
│  - Эскалация: находки, показанные локально и не              │
│    исправленные, получают повышенный приоритет в CI          │
│  - RBAC, апрувы, аудит                                       │
│  - Интеграция с ASOC/ASPM                                    │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  КОНТУР 3: АНАЛИТИЧЕСКИЙ (BI + Compliance)                   │
│  - Метрики воронки эскалации                                 │
│  - Дашборды для каждой роли                                  │
│  - Автоматизация комплаенса (ГОСТ, ФСТЭК)                    │
│  - Доказательство осознанного принятия риска                 │
└─────────────────────────────────────────────────────────────┘
```

### 4.2. Каскадная эскалация

Каждая находка проходит через воронку уровней. Каждый уровень — это фильтр, который пытается решить проблему и передаёт наверх только то, с чем не справился.

| Уровень | Кто | Что пытается | Что передаёт наверх |
|---------|-----|-------------|-------------------|
| **0** | AI-агент | Автоисправить при генерации (patch в коде) | Не получилось — флаг разработчику |
| **1** | Разработчик | Понять, исправить, подавить как FP | Не понял, не смог, проигнорировал — флаг в CI |
| **2** | CI (автоматика) | Заблокировать MR, показать gate | Блокировка → флаг AppSec |
| **3** | AppSec | Триаж, переопределение severity, expert fix | Не решается технически — флаг лиду |
| **4** | Lead / CISO | Принятие риска, изменение политики | — |

**Принцип:** AppSec видит не все находки, а только эскалированные. CISO видит не все риски, а только требующие бизнес-решения. Это сокращение шума на порядок.

### 4.3. Двойной контур gates

Локально и в CI действуют разные правила:

| Параметр | Локально | В CI |
|----------|----------|------|
| CRITICAL | warn | **block** |
| HIGH | warn | **block** |
| MEDIUM | warn | warn |
| LOW | info | info |
| Было показано локально и не исправлено | — | **block (повышенный приоритет)** |
| Новая находка, не показанная локально | — | warn (мягкое предупреждение) |

Ключевое поле конфигурации — `block_on_unresolved_local`: находка, показанная локально и не закрытая, получает повышенный приоритет в CI. Это и есть killer-фича: **не «новая проблема», а «ты знал и решил не чинить»**.

### 4.4. Роли

| Роль | Задача | Ключевые права |
|------|--------|----------------|
| **Developer** | Пишет код, отвечает за свой диф | Сканировать, помечать FP, создавать suppression в своих файлах |
| **Lead** | Контролирует уязвимости команды | Апрувить дифы, управлять SCA, создавать suppression для команды |
| **AppSec** | Эксперт по безопасности | Видеть все находки, создавать локальные кейсы, проводить sec-review, переопределять severity |
| **CISO** | Управляет рисками | Видеть метрики, генерировать отчёты, принимать риск |
| **Admin** | Администрирует систему | Управлять пользователями, проектами, интеграциями |

### 4.5. Жизненный цикл находки

Жизненный цикл отражает прохождение через уровни эскалации:

```
NEW
  │
  ├─ AGENT_FIXED (агент исправил сам — тихо, никто не видит)
  │
  ├─ DEV_SHOWN (показано разработчику локально)
  │    ├─ DEV_FIXED (разработчик исправил)
  │    ├─ DEV_SUPPRESSED (подавил как FP — нужен апрув лида)
  │    └─ DEV_IGNORED (не отреагировал в SLA → эскалация в CI)
  │
  ├─ CI_BLOCKED (CI заблокировал MR)
  │    ├─ DEV_FIXED_AFTER_BLOCK (исправил после блокировки)
  │    └─ ESCALATED_TO_APPSEC (не исправил после SLA → AppSec)
  │
  ├─ APPSEC_TRIAGED (AppSec разобрался)
  │    ├─ APPSEC_FIXED (дал патч/рекомендацию)
  │    ├─ APPSEC_OVERRIDDEN (изменил severity)
  │    └─ RISK_ACCEPTED → ESCALATED_TO_LEAD (бизнес-решение)
  │
  └─ RISK_ACCEPTED (CISO/Lead принял риск — конец)
```

Каждый переход — это событие, которое записывается и видно на дашборде соответствующей роли.

### 4.6. Suppression-стратегия для двойного контура

| Тип suppression | Кто создаёт | Действие локально | Действие в CI | Срок |
|-----------------|-------------|-------------------|---------------|------|
| **Локальный** | Developer | Скрывает в IDE | **Не подавляет** — CI всё равно проверяет | На ветку или файл |
| **CI (team)** | Lead | Синхронизируется вниз — скрывает в IDE | Подавляет в CI | Требует апрув Lead |
| **CI (global)** | AppSec | Синхронизируется вниз — скрывает в IDE | Подавляет в CI | Постоянный или с expiry |

Ключевое правило: **локальный suppression не должен автоматически подавлять CI-находку**. Иначе разработчик подавит всё локально и CI молча пропустит. Обратное работает: CI-suppression синхронизируется вниз, чтобы локально больше не ныло.

### 4.7. SLA и таймеры эскалации

Воронка работает, только если у каждого уровня есть таймер. Иначе разработчик «увидел» и забыл навсегда.

| Уровень | SLA по умолчанию | Что по истечении |
|---------|-----------------|------------------|
| Dev (после показа) | 24 ч | Находка помечается `DEV_IGNORED`, эскалируется в CI |
| Dev (после CI-блока) | 48 ч | Эскалация в AppSec |
| AppSec | 5 раб. дней | Эскалация к лиду/CISO |
| Lead/CISO | 10 раб. дней | Находка становится «overdue risk» |

SLA настраиваемые — разные компании, разные аппетиты.

## 5. Функционал по фазам

### Фаза 1: Локальный MCP-сервер (MVP)

**Цель:** дать разработчику и AI-агенту мгновенную обратную связь по безопасности. Доказать ценность локального скана для себя.

#### 5.1.1. Уровень 0: Автоисправление агентом

AI-агент не только сканирует, но и пытается исправить находку до показа разработчику. Если агент справился — разработчик даже не видит проблему.

| Инструмент | Назначение |
|------------|-----------|
| `auto_fix(finding_id, strategy)` | Попытаться автоматически исправить находку. Возвращает patch или failure_reason |

Хук `PostToolUse` вызывает `auto_fix` перед показом разработчику. Это «уровень 0» в воронке эскалации — бесплатный для разработчика.

#### 5.1.2. MCP-инструменты для AI-агента

| Инструмент | Назначение |
|------------|-----------|
| `scan_file(path)` | Просканировать конкретный файл |
| `scan_diff()` | Просканировать изменения (staged/unstaged) |
| `scan_project(path=".")` | Просканировать весь проект или конкретную директорию |
| `auto_fix(finding_id, strategy)` | Попытаться автоматически исправить находку |
| `get_config()` | Получить текущую конфигурацию |
| `update_config(config)` | Обновить конфигурацию |
| `submit_feedback(finding_id, type, reason)` | Отправить обратную связь (FP, и т.д.) |
| `get_scan_history(limit)` | Получить историю сканирований |
| `suppress_finding(finding_id, reason, expires_at)` | Подавить срабатывание (локально) |

#### 5.1.3. Хуки для AI-агентов

| Хук | Когда срабатывает | Что делает |
|-----|-------------------|-----------|
| `SessionStart` | При старте сессии | Загружает конфигурацию проекта, определяет стек |
| `PreToolUse` | Перед вызовом инструмента | Блокирует опасные операции (запись в защищённые файлы) |
| `PostToolUse` | После вызова инструмента | Триггерит сканирование → `auto_fix` → показ разработчику |

#### 5.1.4. Поддерживаемые сканеры

| Категория | Инструменты |
|-----------|-------------|
| **SAST** | Semgrep, Bandit (Python), ESLint (JS/TS) |
| **Secrets** | Gitleaks, TruffleHog |
| **SCA** | Trivy, OSV-Scanner, Dependency-Track |
| **IaC** | Checkov, KICS |
| **DAST** | OWASP ZAP (базовая интеграция) |

#### 5.1.5. Конфигурация проекта

Файл `.appsecgate-mcp/config.yaml` в корне репозитория:

```yaml
version: 2
stack:
  languages: [python, typescript]
  frameworks: [fastapi, react]

scanners:
  sast:
    enabled: true
    tool: semgrep
    rulesets: [p/security-audit, p/python]
  secrets:
    enabled: true
    tool: gitleaks
  sca:
    enabled: true
    tool: trivy
    severity_threshold: HIGH

gates:
  local:
    warn_on: [CRITICAL, HIGH, MEDIUM]
    block_on: []  # локально не блокируем ничего
  ci:
    block_on: [CRITICAL, HIGH]
    warn_on: [MEDIUM]
    block_on_unresolved_local: true  # блокируем то, что видели локально и не чинили

auto_fix:
  enabled: true
  strategies: [patch, suggestion]
  max_attempts: 1  # один раз пытаемся, потом — разработчику

suppress:
  - rule: insecure-random
    paths: [src/utils/random.ts]
    reason: "Non-crypto use only"
    scope: local  # local | ci | global

sla:
  dev_response: 24h
  dev_after_block: 48h
  appsec_response: 5d
  lead_response: 10d
```

#### 5.1.6. Локальное хранилище

- `~/.appsecgate-mcp/cache/` — кэш сканов
- `~/.appsecgate-mcp/credentials` — токен для master-сервера
- `~/.appsecgate-mcp/feedback.db` — локальная база обратной связи (для офлайна)
- `~/.appsecgate-mcp/shown_findings.db` — журнал показанных находок (для будущего CI-контура)

**Важно:** даже в Фазе 1 (без master-сервера) локально логируется, какие находки были показаны разработчику. Это данные для будущего CI-контура: если в CI приходит та же находка (по fingerprint) и она была показана локально, но не исправлена — gate работает жёстче.

#### 5.1.7. Критерии готовности фазы 1

- [ ] MCP-сервер запускается одной командой
- [ ] Поддерживает Claude Code, Cursor, Cline
- [ ] Сканирует diff за < 5 секунд
- [ ] `auto_fix` работает для топ-5 правил
- [ ] Работает офлайн (с кэшем)
- [ ] Логирует показанные находки в `shown_findings.db`
- [ ] Документация по установке и настройке
- [ ] **3+ разработчика используют в ежедневной работе 2+ недели** (не просто установили — сканировали код через неделю после установки)

### Фаза 2: Master-сервер и CI-контур

**Цель:** дать команде единый источник правды, синхронизировать локальные и CI-сканы, включить двойной контур gates.

#### 5.2.1. Основные функции

| Функция | Описание |
|---------|----------|
| **Централизованная конфигурация** | Политики, правила, пороги, SLA — на сервере |
| **Синхронизация находок** | Все находки со всех машин и CI — в одной базе |
| **Finding Fingerprint** | Детерминированный ID для сопоставления находок между локальным и CI-сканом |
| **Двойной контур gates** | Локально — warn-only, CI — block с `block_on_unresolved_local` |
| **Baseline** | Эталонный скан для каждой ветки |
| **Delta API** | Показывает только новые проблемы |
| **Real-time уведомления** | WebSocket для синхронизации между разработчиками |
| **Аудит** | Кто, что, когда изменил |
| **SLA-таймеры** | Автоматическая эскалация по истечении SLA |

#### 5.2.2. Finding Fingerprint

Детерминированный ID для сопоставления находок между локальным и CI-сканом. Нетривиальная задача: код сдвинулся на строку — fingerprint не должен сломаться.

**Подход:** fingerprint = hash(rule_id + file_path + normalized_code_snippet). Нормализация убирает пробелы, комментарии и сдвиги строк. Отдельный спайк на прототип fingerprinting до начала фазы.

#### 5.2.3. Синхронизация с CI (GitLab)

- Запуск security-джобы в CI через `.gitlab-ci.yml`
- Загрузка результатов в master-сервер
- Сравнение с локальными сканами по fingerprint
- Логика эскалации:
  - Находка была `SHOWN_LOCALLY` и не `FIXED_LOCALLY` → **block** (осознанное игнорирование)
  - Находка новая в CI (не было `SHOWN_LOCALLY`) → **warn** (возможно, сканер локально не покрыл файл)
- Генерация SARIF-отчётов для GitLab Security Dashboard

#### 5.2.4. Синхронизация с ASOC

- Экспорт находок в DefectDojo, R-Vision, PT ASM
- Обновление состояния находок (FIXED_LOCALLY → FIXED_VERIFIED)
- Двусторонняя синхронизация (ASOC → SG и SG → ASOC)

#### 5.2.5. Suppression-синхронизация

- Локальный suppression **не** подавляет CI-находку
- CI-suppression (Lead/AppSec) синхронизируется вниз — скрывает в IDE
- Синхронизация через master-сервер

#### 5.2.6. Критерии готовности фазы 2

- [ ] REST API для всех операций
- [ ] WebSocket для real-time
- [ ] Finding Fingerprint прототипирован и работает
- [ ] Двойной контур gates (local warn + CI block)
- [ ] `block_on_unresolved_local` работает
- [ ] Интеграция с GitLab CI/CD
- [ ] Интеграция с DefectDojo (минимум)
- [ ] SLA-таймеры и автоэскалация
- [ ] Развёртывание через Docker Compose
- [ ] 3+ команды используют в продакшене

### Фаза 3: Разделение на роли (RBAC) и Workflow

**Цель:** дать каждой роли свои права и инструменты. Включить уровни эскалации 3 и 4 (AppSec, Lead/CISO).

#### 5.3.1. Роли и права

| Право | Developer | Lead | AppSec | CISO | Admin |
|-------|-----------|------|--------|------|-------|
| `scan:run` | ✅ | ✅ | ✅ | ✅ | ✅ |
| `finding:view:own` | ✅ | ✅ | ✅ | ✅ | ✅ |

### Фаза 4: BI-аналитика и метрики воронки

**Цель:** дать руководству и AppSec прозрачную картину эффективности безопасности.

#### 5.4.1. Метрики воронки эскалации

Ключевая группа метрик — измерение эффективности каскадной эскалации:

| Метрика | Что измеряет |
|---------|-------------|
| **Agent Fix Rate** | % находок, исправленных агентом без участия человека |
| **Dev Self-Service Rate** | % находок, исправленных разработчиком без AppSec |
| **AppSec Escalation Rate** | % находок, дошедших до AppSec |
| **CI Block Rate** | % MR, заблокированных в CI |
| **Risk Acceptance Rate** | % находок, принятых как риск |
| **Mean Time to Escalate** | Среднее время прохождения воронки от NEW до RISK_ACCEPTED |

**Доказательство ROI:** если Agent Fix Rate = 30%, Dev Self-Service = 50%, то AppSec видит только 20%. Это и есть ценность продукта, выраженная в цифрах.

#### 5.4.2. Дашборды

| **AppSec Dashboard** | AppSec | Эскалированные находки, топ шумных правил, shift-left метрики |
| **Executive Dashboard** | CISO | Risk Score, воронка эскалации, ROI, комплаенс |
| **Compliance Dashboard** | CISO, AppSec | Готовность к ГОСТ Р 56939, ФСТЭК |

## 6. Дорожная карта

### 6.1. Основная последовательность

| Фаза | Название | Длительность | Ключевой результат |
|------|----------|--------------|-------------------|
| **1** | Локальный MCP | 2–3 месяца | MCP-сервер, `auto_fix`, warn-only, офлайн, 3+ активных пользователя |
| **2** | Master + CI | 3–4 месяца | REST API, двойные gates, fingerprint, GitLab, DefectDojo, SLA |
| **3** | Роли (RBAC) | 2–3 месяца | 5 ролей, апрувы, эскалация AppSec/Lead, аудит |
| **4** | Web + BI | 2–3 месяца | Дашборды, метрики воронки, отчёты |
| **5** | РБПО | 4–6 месяцев | Диагностика, доказательства, сертификация |

**Итого:** 13–19 месяцев до полноценной платформы.

### 6.2. Приоритеты

1. **MVP (Фаза 1):** доказать ценность локального скана для себя. Пожить с инструментом 2–3 недели на своём проекте.
2. **Product-Market Fit (Фазы 2–3):** доказать ценность для команды. Найти первого платного клиента.
3. **Scale (Фазы 4–5):** доказать ценность для бизнеса.

### 6.3. Параллельный трек: ГОСТ-микро-проект

ГОСТ/SSDLC может быть выделен в отдельный микро-проект и запущен **параллельно** с Фазами 1–2. Это независимая монетизируемая единица.

**Минимум для микро-проекта:**
- Опросник по 10 разделам ГОСТ Р 56939
- Gap-анализ
- Маппинг артефактов из GitLab/Jira
- PDF-отчёт

**Почему это работает как отдельный продукт:**
- Целевая аудитория (вендоры ПО, которым нужна сертификация) — чёткая
- Боль острая, готовность платить высокая
- Не зависит от MCP-сервера, master-сервера или RBAC
- Технически: те же навыки нормализации данных, что в Фазе 1

**Связь с основным продуктом:** Фаза 1 учит оборачивать сканеры и нормализовать результаты. ГОСТ-модуль использует тот же навык — только результаты идут не в MCP-клиент, а в evidence-базу. Фаза 1 — технический спайк для ГОСТ-модуля.

### 6.4. Что можно ускорить

- **Фаза 3 (роли):** можно начать параллельно с Фазой 2, если есть ресурсы.
- **Фаза 4 (BI):** можно использовать Metabase с первого дня, не строить свой UI.
- **Фаза 5 (РБПО):** можно начать с консалтинга, автоматизируя постепенно.
- **Customer discovery:** 5–7 интервью по ГОСТ можно провести параллельно с Фазой 1.

### 6.5. Open-source стратегия

Рассматриваемая модель: MCP-сервер (Фаза 1) — open-source, master-сервер (Фаза 2+) — платный. Это снижает барьер входа и создаёт воронку.
